# Repository streamlining — branch cleanup analysis

Goal: reduce the repo to **two long-lived branches — `dev` and `prod`**.

This document is the audit behind that cleanup. It was generated by analyzing
all 43 remote branches against the 71 pull requests (using PR *merged* status,
since the repo uses squash-merges — plain git ancestry reports squash-merged
branches as "unmerged").

## TL;DR

1. **15 branches are fully merged** (their PR was merged; their work lives in a
   kept branch). These are safe to delete with zero work loss — see the script
   below. Deletion could **not** be performed automatically: this environment's
   git proxy returns `403` on `git push --delete`, and the GitHub tooling has no
   delete-branch/ref capability. **You must run the script yourself** (or delete
   them from the GitHub branches UI).

2. **Reaching literally two branches is blocked by real divergence.** `a4ot`,
   `main`, `dev`, and `production` are four *parallel* lines, each holding large
   amounts of unique, unmerged work:

   | branch      | commits NOT in a4ot | last commit  |
   |-------------|---------------------|--------------|
   | `a4ot`      | — (chosen as prod)  | 2026-05-31   |
   | `main`      | 126                 | 2026-04-15   |
   | `dev`       | 88                  | 2026-01-19   |
   | `production`| ~90                 | 2026-03-03   |

   `a4ot` is the *newest by date* but is **not a superset** — it is missing the
   Deno Fresh migration, Twilio OTP, Tor DNS monitoring, sequential gate
   questions, shared nav assets, and more that live in `main`/`dev`/`production`.
   Collapsing these into one `prod` requires either **merging** the lines
   (conflict-prone reconciliation) or **discarding** the unmerged work — a
   decision for the repo owner, not something to force by reset.
